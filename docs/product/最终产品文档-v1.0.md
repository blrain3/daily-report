| 报告日 | 运行启动时刻在上海时区的日期。 |
| 首次入库归属 | 记录归入首次写入数据库的那一轮报告日。 |

## 4. 系统设计

本章给出模块边界、数据约束与从启动到收尾的执行规则。

### 4.1 总体架构

分层结构见图 A-1（见附录 A）。

| 层 | 职责 | 依赖方向 |
|---|---|---|
| 配置层 | 加载三份 YAML、校验环境变量引用、提供成员索引和工作日判定。 | 依赖文件和进程环境，向上提供配置。 |
| 采集层 | 组装各源窗口，执行分页、超时重试、飞书 token 管理和外部字段标准化。 | 依赖配置、外部 API 和编排器传入的水位。 |
| 归属与去重层 | 匹配成员、脱敏、生成记录键、提交记录与水位。 | 依赖采集结果、成员索引和 SQLite。 |
| 渲染层 | 按报告日取数，生成 Markdown 与 HTML，管理版本文件和补渲染。 | 依赖持久化视图、配置和文件系统。 |
| 推送层 | 分别管理 SMTP 与飞书正文、推送键和发送状态。 | 依赖渲染产物、凭据引用、推送日志和远端通道。 |
| 运行保障层 | 编排其余各层，管理时钟、文件锁、轮次状态、调度、诊断和告警。 | 包装脚本调用编排入口，各业务层通过统一日志接口记录诊断。 |

采集器仅返回结果，数据库写入由编排器串行组织。渲染从数据库取数，因此常规重跑与历史恢复复用同一路径。外部正文和错误文本均先全文脱敏再截前 80 字。大陆手机号、邮箱之外长度至少 8 的字母数字或 `_-` 连续串、已知 token 前缀后的值和密码类赋值均按规则识别；替换保留前 4 后 2，中间为 `***`，已识别且不足 8 字的值整体替换。见规格 §2.3。

### 4.3 数据模型

以下为 SQLite 建表设计。日期键使用 `YYYYMMDD`，时间戳统一采用含 `+08:00` 的固定格式。可空成员使用 SQL NULL。源状态和通道状态的枚举细化为本文设计，未执行的步骤可保留 NULL。

```sql
CREATE TABLE run (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    status TEXT NOT NULL CHECK (status IN ('running','success','partial','failed')),
    report_file TEXT,
    failure_reason TEXT,
    note TEXT,
    github_status TEXT CHECK (github_status IN ('success','failed')),
    github_error TEXT,
    feishu_task_status TEXT CHECK (feishu_task_status IN ('success','failed')),
    feishu_task_error TEXT,
    feishu_message_status TEXT CHECK (feishu_message_status IN ('success','failed')),
    feishu_message_error TEXT,
    smtp_status TEXT CHECK (smtp_status IN ('success','failed','skipped')),
    smtp_error TEXT,
    feishu_push_status TEXT CHECK (feishu_push_status IN ('success','failed','skipped')),
    feishu_push_error TEXT,
    CHECK (
        (status = 'running' AND finished_at IS NULL AND report_file IS NULL)
        OR (status = 'failed' AND finished_at IS NOT NULL AND report_file IS NULL)
        OR (status IN ('success','partial') AND finished_at IS NOT NULL
            AND report_file IS NOT NULL AND length(report_file) > 0)
    )
);
CREATE INDEX run_history ON run(started_at, status);

CREATE TABLE source_state (
    source TEXT PRIMARY KEY NOT NULL
        CHECK (source IN ('github','feishu_task','feishu_message')),
    last_started_at TEXT,
    last_status TEXT NOT NULL CHECK (last_status IN ('success','failed'))
);

CREATE TABLE seen_item (
    item_key TEXT PRIMARY KEY NOT NULL CHECK (length(item_key) > 0),
    source TEXT NOT NULL CHECK (source IN ('github','feishu_task','feishu_message')),
    occurred_at TEXT NOT NULL,
    first_seen_report_date TEXT NOT NULL
        CHECK (length(first_seen_report_date) = 8
               AND first_seen_report_date NOT GLOB '*[^0-9]*'),
    member TEXT,
    text_summary TEXT NOT NULL CHECK (length(text_summary) <= 80),
    raw_id TEXT NOT NULL CHECK (length(raw_id) > 0),
    render_metadata TEXT NOT NULL DEFAULT '{}'
);
CREATE INDEX seen_item_report ON seen_item(
    first_seen_report_date, source, member, occurred_at, item_key
);
CREATE TRIGGER seen_item_report_date_immutable
BEFORE UPDATE OF first_seen_report_date ON seen_item
WHEN NEW.first_seen_report_date <> OLD.first_seen_report_date
BEGIN
    SELECT RAISE(ABORT, 'first_seen_report_date is immutable');
END;

CREATE TABLE report_version (
    report_date TEXT PRIMARY KEY NOT NULL
        CHECK (length(report_date) = 8 AND report_date NOT GLOB '*[^0-9]*'),
    latest_version INTEGER NOT NULL DEFAULT 0
        CHECK (typeof(latest_version) = 'integer' AND latest_version >= 0)
);

CREATE TABLE push_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    report_date TEXT NOT NULL
        CHECK (length(report_date) = 8 AND report_date NOT GLOB '*[^0-9]*'),
    channel TEXT NOT NULL CHECK (channel IN ('smtp','feishu')),
    member_set TEXT NOT NULL,
    content_sha256 TEXT NOT NULL
        CHECK (length(content_sha256) = 64 AND content_sha256 NOT GLOB '*[^0-9a-f]*'),
    status TEXT NOT NULL CHECK (status IN ('sending','success','failed','superseded')),
    error TEXT,
    note TEXT,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    CHECK (status <> 'sending' OR finished_at IS NULL),
    CHECK (status NOT IN ('success','failed') OR finished_at IS NOT NULL),
    CHECK (status <> 'failed' OR error IS NOT NULL)
);
CREATE INDEX push_log_lookup ON push_log(
    report_date, member_set, channel, content_sha256, status
);
CREATE UNIQUE INDEX push_log_success ON push_log(
    report_date, member_set, channel, content_sha256
) WHERE status = 'success';
```

`render_metadata` 是本文建议的同表扩展，以 JSON 保存前后任务状态、脱敏后的未归属发送人或负责人显示标签及代码增删行数等复渲染所需字段。应用按来源校验形状，外部文本沿用脱敏规则。应用校验实际日期、时区及来源与键格式；建表约束校验基础形状。见规格 §2.3、§2.6、§2.8。

| 表 | 写入时机与事务边界 |
|---|---|
| `run` | 获锁并通过启动检查后独立提交 `running`；转终态另开事务，更新时间、文件路径及分源和通道结果。历史补渲染独立更新相关轮次备注。 |
| `source_state` | 记录各源最近状态，成功源的水位在允许出报时与本轮记录同事务推进。无已有行等价于无水位。 |
| `seen_item` | 与水位使用同一 `BEGIN IMMEDIATE` 事务，主键冲突仅跳过该记录，其余错误回滚整批。崩溃发生在提交前时从旧水位重读。 |
| `report_version` | 同日首个成功文件编号为 1，正常与补渲染共用计数。在锁内完整写临时文件后原子发布，发布成功后独立提交版本计数。 |
| `push_log` | 发送前独立提交 `sending`，外部调用在事务外执行。结果到达后用独立事务填写终态，成功行及旧行结清原子提交。 |

文件系统与 SQLite 的提交各自独立。实现时建议在锁内核对版本计数及现有文件，识别发布后、计数提交前留下的完整版本，防止复用编号并覆盖文件。历史最新文件已丢失时仍从持久化计数向后取号。历史 `superseded` 与同键 `success` 的不变量由应用写入事务维护，读取时仍识别存量异常。见规格 §2.6–§2.8。

### 4.4 核心流程

执行时序见图 A-2，推送判定见图 A-3（见附录 A）。

#### 4.4.1 单轮执行

1. 启动即冻结上海时区的 `started_at`。装载本地配置并判断工作日，非工作日跳过。获取排他文件锁，竞争失败记录 ERROR 并以非零退出，采集、写库与日报推送均不启动。通过凭据检查及飞书身份能力自检后，独立写入并提交 `running`。见规格 §2.1、§2.2、§2.4、§2.8–§2.10。
2. 在本轮采集前扫描历史 `success`、`partial`、`failed`、`running` 轮次，筛选文件路径为空或文件不存在的轮次，并按报告日合并候选。对缺有效最新版本的日期做全量补渲染；仅由 `failed` 或 `running` 轮次形成的候选须有该日已入库记录。补渲染沿用版本计数，不触发重采、水位推进或自动补发。成功在 `run.note` 和日志标注「已补渲染 YYYYMMDD vN，需人工确认是否补发」，失败记 ERROR 后继续本轮，两个结果均供包装脚本告警汇总。见规格 §2.6、§2.10.3。
3. 读取三源水位，并发采集。窗口为 `(下界, started_at]`。有水位时完整扫描水位以来的区间；无水位时取上一工作日 00:00 与 `started_at − 72 小时` 中更晚者。单请求 15 秒，单源 35 秒含最多 3 次重试及 2/4/8 秒退避；飞书 token 失效时刷新一次并重试，计入该源预算。整轮到 45 秒阈值异步取消在途采集，失败段注明原因。见规格 §2.5、§2.11。
4. 规范化、归属、脱敏后按键插入记录。三源成功且可出报，推进三源；部分源失败且可出报，仅推进成功源；全源失败或无可渲染数据，保留全部水位、放弃出报并立即写 `failed`。有旧水位的失败源下轮从原水位补采，无水位的失败源下轮重新计算下界。见规格 §2.8。
5. 对可出报轮次，按报告日全量渲染，落盘后生成待推送正文，分别执行 SMTP 与飞书判定。写 `success`（三源成功并出报）或 `partial`（部分源失败仍出报），同时保存通道结果。任一日报通道发送失败时保留文件并以非零退出。退出时释放锁，进程异常退出时操作系统释放锁。见规格 §2.6–§2.10。

入库事务提交后若渲染失败，建议在锁内对可捕获异常以独立事务还原本轮已推进的水位，再写 `failed`，保留已入库记录供补渲染。若进程直接崩溃，保留 `running` 作为恢复入口，已提交的水位有对应记录。稳定性验收需覆盖这两个时点。补渲染事项纳入非零退出告警；当日报正常且退出码为 0 时，规格未规定独立告警触发规则，待实现阶段确认，事项仍可由日志与备注追踪。

#### 4.4.2 记录归属链路

| 环节 | 处理 |
|---|---|
| 源内过滤 | GitHub 按仓库、作者和窗口过滤，读取提交 SHA、首行、提交时间和增删行；任务采集创建、进入进行中或已完成的独立事件；消息同时满足白名单、关键词和窗口。 |
| 人员映射 | 按 `author.login → github` 精确匹配；飞书优先 `open_id → feishu_open_id`，仅有显示名或对应成员未配置绑定时按 `name` 精确回退。两个身份字段均不可用时，自检报错退出。可解析但无法匹配的任务或消息进入未归属段。 |
| `item_key` | 提交 `github:<sha>`、任务 `feishu_task:<task_id>:<event_type>:<changed_at>`、消息 `feishu_msg:<message_id>`。 |
| `seen_item` | 去重成功的新增记录写入发生时间、匹配成员、摘要、原始标识及 `first_seen_report_date`，此后保留首次入库日期。 |
| 渲染筛选 | 按 `first_seen_report_date = 报告日` 读取全部记录，按代码提交、任务进展、协作沟通展示；空成员写「今日无记录」，无绑定写「无飞书绑定」。 |
| 版面提示 | 按适用场景在首页第一段写「注意：本次为首次运行或无水位，早于 <时间> 的记录未包含」，在页脚写节假日配置回退提示。 |

用 Python-Markdown（含表格和围栏代码支持）生成邮件 HTML。建议固定记录排序和正文序列化，日志时间、版本号等运行元数据留在正文之外，使相同内容的摘要保持稳定。跨日补采以首次入库轮次归属，节后验收口径见 §6.1。见规格 §2.3–§2.7。

#### 4.4.3 推送有序判定

以报告日、按姓名排序并无歧义拼接的成员集合、通道和该通道正文的 SHA-256 为键。对 SMTP 的 HTML 与飞书的 Markdown 分别判定，命中即结束本次选路。

| 优先级 | 同键历史 | 行为 |
|---|---|---|
| 1 | 存在 `success` | 跳过该通道，即使还有 `sending`。 |
| 2 | 无 `success`，存在 `sending` | 重发一次，在 `push_log.note` 和日志标注「可能重复：上次发送结果未知」；成功时所有旧 `sending` 转 `superseded`。 |
| 3 | 仅有 `failed`、仅有 `superseded`、二者并存或无记录 | 正常发送；若仅有 `superseded` 则按无记录处理并记 WARN。成功后同键旧残留统一结清为 `superseded`。 |

每次实际发送先写新的 `sending`，调用结束后原地改为 `success` 或 `failed` 并记结束时间，失败记原因。每通道有独立的 30 秒超时。发送成功判定与本地记账之间存在崩溃窗口，采用 at-least-once 重试语义。同键每次重跑最多重发一次，多轮反复在该窗口崩溃时累计重复次数无上限。见规格 §2.7、§2.11。

### 4.5 关键设计决策与取舍

| 问题 | 方案 | 为什么不用另一个 |
|---|---|---|
| 每轮扫描多少数据 | 每源用独立水位读取增量。 | 全量快照重复分页和拉取历史，且不利于隔离单源失败。 |
| 重叠时如何去重 | 使用来源与原始标识构造记录键，任务再纳入事件类型和时间。 | 时间窗口去重难以区分同一时刻的不同事件，也无法稳定识别跨轮重读。 |
| 跨日数据归属 | 用首次入库报告日，`occurred_at` 用于展示和排序。 | 用事件日会让晚间、周末和故障恢复时补采的记录落入此前的日期，常规出报难以覆盖。 |
| 何时推进水位 | 记录插入和水位推进同事务。 | 分两次提交若先保存水位，进程崩溃会跳过尚未落库的区间。 |
| 可否保证只送一次 | 按通道键识别已知成功，结果未知时带标记重发。 | 远端接收与 SQLite 提交无法同事务，无法证明崩溃前是否已送达。 |
| 补渲染后如何处理 | 恢复版本文件，留下人工补发事项。 | 自动补发可能重复发送历史正文，也可能在当前时间投递过期通知。 |
| 调休如何触发 | 每日调度，由程序读取工作日表。 | 固定周一至周五触发会漏掉调休上班的周末。 |

### 5.3 部署方式

| 方式 | 实施要点 |
|---|---|
| Docker | Dockerfile 采用 Python 3.11 或更新版本的精简基础镜像，安装时区数据、CA 证书与锁工具，安装锁定版本的 Python 依赖，复制源码和可执行包装脚本。设置 `WORKDIR /opt/daily-report`、非 root 运行用户和 `ENTRYPOINT ["./bin/run_daily.sh"]`。调度器单次启动容器并传递进程退出码。 |
| 容器持久化 | 分别挂载三份配置文件与 `data/`、`reports/`、`logs/`，运行目录须可写。容器部署把 `lock_file` 指向共享持久卷内路径，例如 `./data/daily-report.lock`，使共享同一数据库的批处理实例竞争同一文件锁。运行器从受控环境按变量名转发凭据。 |
| 裸机 | 在 `/opt/daily-report` 安装程序与 Python 3.11+ 虚拟环境，包装脚本调用虚拟环境解释器。以专用账号运行，确保三份 YAML 可读、持久化目录与锁文件可写，凭据对调度进程可用。 |

以下配置在包装脚本和运行环境就绪后可使用。cron 与 systemd timer 二选一，两个示例均每日触发并由程序处理调休。相对路径统一以 `/opt/daily-report` 为基准。容器方式可将包装脚本调用替换为调用 Docker 的宿主机启动脚本。见规格 §2.9、§2.10、§2.13。

部署到支持 `CRON_TZ` 的 cron，以下内容放入运行账号的 crontab。预先建立 `logs/`，由部署启动环境为任务注入凭据。

```cron
CRON_TZ=Asia/Shanghai
0 18 * * * cd /opt/daily-report && ./bin/run_daily.sh >> ./logs/cron.log 2>&1
```

systemd 示例使用运行账号的用户级 unit。把两个文件放入 `~/.config/systemd/user/`，由部署环境向用户服务管理器提供 §5.2 的变量，按需配置用户注销后继续运行。日历表达式直接指定 IANA 时区。 [systemd 日历表达式](https://www.freedesktop.org/software/systemd/man/latest/systemd.time.html)

`daily-report.service`

```ini
[Unit]
Description=Daily report batch

[Service]
Type=oneshot
WorkingDirectory=/opt/daily-report
Environment=TZ=Asia/Shanghai
ExecStart=/opt/daily-report/bin/run_daily.sh
```

`daily-report.timer`

```ini
[Unit]
Description=Run daily report at 18:00 Asia/Shanghai

[Timer]
OnCalendar=*-*-* 18:00:00 Asia/Shanghai
AccuracySec=1s
Unit=daily-report.service

[Install]
WantedBy=timers.target
```

安装后运行 `systemctl --user daemon-reload` 和 `systemctl --user enable --now daily-report.timer`，用 `systemctl --user list-timers` 核对触发时间。

| 首次部署检查 | 操作 |
|---|---|
| 配置与时钟 | 核对成员唯一性、仓库和采集群白名单、日报与告警目标、上海时区与生效工作目录。 |
| 凭据与连通 | 检查环境变量引用及权限，验证目标仓库、任务事件、群历史、机器人与 SMTP 的连通性。 |

| 首轮验证 | 使用测试仓库、测试群和测试收件账号，按 §6 核对首页提示、版本文件、数据库状态及送达。 |

每年初按国务院办公厅当年通知维护 `year`、`holidays` 与 `workdays`，逐项核对年份、节日和调休周末。遇到跨年窗口时，按日期所属年份检查覆盖和回退。

应用日志位于 `logs/daily-report-YYYYMMDD.log`，调度输出见 `logs/cron.log` 或 `journalctl --user -u daily-report.service`。先用 `run` 关联源和通道状态，再查 `source_state` 水位与 `push_log` 失败或未知结果。非零退出由包装脚本按独立告警目标送出退出码、报告日、失败摘要与日志路径，并列出适用的补渲染事项及报告日和版本。两目标都不可用时记录 ERROR「告警通道不可用」并保留原退出码。见规格 §2.10。

| 常见故障 | 处置 |
|---|---|
| token 过期 | 飞书先走一次刷新和原请求重试；刷新失败或 GitHub 凭据失效时检查授权和变量注入，更新凭据后受控重跑。 |
| 限流 | 检查响应和单源预算，核对失败标注及水位，限流解除后再重跑并确认对应区间补采。 |
| 锁未释放 | 检查持锁进程及容器状态；锁文件存在可能只有路径残留。确认旧实例退出并由系统释放锁后再重跑，避免删除仍被持有的锁文件。 |

三张图分别对应 §4.1 的分层结构、§4.4 的执行时序与推送判定。图源为 PlantUML 文件，随仓库放在 `diagrams/` 目录下（`arch.puml`、`sequence.puml`、`push-state.puml`），修改后执行 `plantuml -tpng diagrams/*.puml` 重新出图。

![](diagrams/arch.png){width=15.5cm}

**图 A-1 总体架构**

架构按职责分层：运行保障层负责调度、互斥与状态机；配置层提供三份配置与凭据引用；采集层向外部服务取数；归属与去重层完成身份映射、记录去重与水位推进；渲染与推送层产出日报版本并决定是否发送。依赖方向自上而下，下层不反向引用上层。

![](diagrams/sequence.png){width=13.5cm}

**图 A-2 一轮执行时序**

时序要点有三处：`run(status='running')` 在采集之前独立提交，使崩溃轮可被下一轮识别并补渲染；`seen_item` 插入与水位推进在同一事务内提交；`success`/`partial` 终态在日报文件落盘之后写入，`failed` 在放弃出报时立即写入。

![](diagrams/push-state.png){width=12cm}

**图 A-3 推送状态机**

单通道按推送键判定：同键已有 `success` 时无条件跳过；无 `success` 但残留 `sending`（结果未知）时重发一次并标注「可能重复」；其余情形正常发送，成功后把同键旧行统一结清为 `superseded`。该状态机只保证 at-least-once，不承诺去重。

## 附录 B 术语表

本附录统一规格第 4 节的术语在本文中的含义。

| 术语 | 定义 |
|---|---|
| 日报 | 按代码、任务、沟通三部分组织的团队工作记录。 |
| 成员 | 在 `members.yaml` 登记且具有 GitHub 登录名的人员。 |
| 数据源 | GitHub 提交、飞书任务、飞书消息三类外部输入。 |
| 增量采集窗口 | 各源上次成功推进的 `started_at` 到本次 `started_at`，左开右闭；无水位见规格 §2.5。 |
| 水位 | `source_state.last_started_at`，三源独立维护。 |
| 报告日 | `started_at` 的上海时区日期；记录沿用首次入库时保存的报告日。 |
| `item_key` | `seen_item` 中标识一条源记录或任务事件的主键。 |
| 原文片段 | 全文脱敏后截取的前 80 字。 |
| 工作日 | 节假日表判定为工作的日期，缺少覆盖时按周一至周五处理。 |
| 未归属段 | 任务或沟通部分收纳未匹配成员的记录的小节。 |
| 日报版本 | 文件名中的 `v{N}`，按报告日递增并保留旧版。 |
| 推送键 | `(report_date, member_set, channel, content_sha256)`。 |
| 时区 | 全系统统一使用 Asia/Shanghai（UTC+8）。 |
