## 2. 新引入的问题（v1.1 相对 v1.0 新增或修后暴露）

### P0

**N1 采集窗口重叠，「执行记录用作下次窗口依据」在成功路径上落空（2.1.3 vs 2.1.3、3.3）**

2.1.3 定义「采集窗口 = 上一工作日 00:00 至本次执行时刻」。周二 18:00 执行时，窗口为周一 00:00–周二 18:00；而周一 18:00 的日报已覆盖周一 00:00–18:00，于是周一白天的提交/任务/消息会在周一、周二两份日报中重复出现。周一执行时窗口「从上周五 00:00 起算」（3.3）同样把周五白天重复计入周一日报。2.1.3 又写「每次执行成功后写入一条执行记录……用作下次窗口计算的依据」，但成功路径根本不需要读上次记录（只用「上一工作日 00:00」），该句只在失败回溯路径成立，与定义自相矛盾。

- 建议：窗口起点改为「上次成功执行时刻」（周一自然从周五 18:00 起算，覆盖周末且不与周五日报重叠）；仅当上次成功记录缺失或距今超过 72 小时时按回溯与截断规则处理。同步改 2.1.3、3.3、4。

**N2 「避免重复推送」与 2.1.5 的推送行为矛盾（2.1.6 vs 2.1.5）**

2.1.6 称「重跑同一天时更新既有记录而非新增，避免重复推送与重复留档」。SQLite 的 upsert 只能避免重复留档，管不到推送；2.1.5 没有任何「已推过则跳过」的条件，重跑同一天会再次发邮件、再次发飞书。文档承诺了一个其机制无法达成的结果。

- 建议：二选一并写清——(a) 增加推送记录/幂等键，重跑时内容无变化则不重推；(b) 删去「避免重复推送」承诺，明示重跑会重复推送。同时给 3.5 或 3.4 补对应验收。

**N3 发送人聚合与「每位成员一段」之间的映射未定义（2.1.2、2.1.4 vs 2.1.1）**

2.1.2 要求群消息「按发送人聚合」，2.1.4 要求「每位成员一段」，但文档未规定：群消息发送人不在 `members.yaml` 中、或成员缺 `feishu_open_id` 时，这些片段落入哪个段落（丢弃？单独「未归属」段？）。同理，飞书任务「负责人」到底返回 open_id 还是显示名未说明——若接口返回显示名，2.1.1「`feishu_open_id` 用于匹配任务负责人」就无法实施。这是「按成员分段」这一核心产物的前置条件缺失，会直接卡住实现。

- 建议：明确匹配键（接口返回字段 → `members.yaml` 字段），并规定未匹配到成员的消息/任务进入「未归属」段还是计数后丢弃；在 2.1.2 或 2.1.4 落一条规则。

### P1

**N4 3.2 的 commit 验收口径与 2.1.2 矛盾（3.2 vs 2.1.2）**

3.2 第一条为「能获取配置仓库内、采集窗口内全部成员的 commit 记录（不只作者为成员的提交）」。括号「不只作者为成员的提交」与 2.1.2「获取 `members.yaml` 中各 `github` 用户在配置仓库内、采集窗口内的提交」互相打架：按字面，验收似乎在要求采集非成员作者的提交。应改为「对每个成员的 `github` 用户，获取其在配置仓库、采集窗口内的全部 commit，且不采集作者不在 `members.yaml` 中的提交」。

**N5 `email` 必填却无消费方，校验规则与验收未覆盖（2.1.1、3.1 vs 2.1.5）**

2.1.1 将 `email` 标为必填，说明是「收件地址」；但 2.1.5 又写「Leader 收件地址独立配置，不占用成员 `email`」。本期没有任何功能消费成员 `email`，却强制必填，属新增的「必填无用字段」。同时 2.1.1 声称 `name` 与 `github` 均「全局唯一」并要校验重复，3.1 只验收了 `github` 重复；`email` 缺失、YAML 解析失败在 2.1.1 有规则但 3.1 无验收。

- 建议：要么删去 `email`，要么写明其用途（如未来个人推送预留）并改为可选；3.1 补 `name` 重复、`email` 缺失、YAML 解析失败三条。

**N6 `config.yaml` 有引用无结构（2.4、5）**

2.4 列出 `config.yaml`（关键词表、仓库列表、SMTP 与飞书凭据引用），第 5 节称「`holidays.yaml` 与 `config.yaml` 的结构见 2.2 与 2.4」，但 2.2 只给了 `holidays.yaml`，2.4 只列了内容名目，没有任何 `config.yaml` 的 schema 或示例。关键词表是列表还是逗号串、仓库列表字段名是什么、凭据引用是文件路径还是环境变量名，均不可知，无法据此实现配置加载。

- 建议：补 `config.yaml` 示例文件或字段表（关键词表格式、仓库列表格式、凭据引用方式），并修正第 5 节的指向。

**N7 飞书 token 刷新只出现在验收标准，正文无功能定义（3.7 vs 2.1.2、2.5）**

3.7 要求「飞书 token 过期时自动刷新一次并重试，刷新失败则按数据源失败处理」，但 2.1.2 与 2.5 从未提到 token 刷新，其耗时是否计入 15 秒/45 秒预算也未定义。验收标准引入了正文不存在的功能。

- 建议：在 2.1.2 或 2.5 补一句 token 刷新规则，并注明刷新耗时计入该数据源预算。

**N8 3.3 硬编码「上周五」与「上一工作日」在节假日场景冲突；3.6 未覆盖「文件缺失」分支（3.3、3.6 vs 2.1.3、2.2）**

3.3 写「周一执行时，窗口从上周五 00:00 起算」，但按 2.1.3 的「上一工作日」语义，若上周五是法定节假日，周一的窗口起点应是更早的工作日（如周四）00:00。3.3 的固定表述与节假日规则冲突。2.2 规定「文件缺失或未覆盖当年时」回退周一至周五并标注，3.6 只验收了「未配置当年节假日表」一种情况。

- 建议：3.3 改为「以 2.1.3 计算窗口起点（上一工作日 00:00，遇节假日继续前溯）」，3.6 补「holidays.yaml 缺失」用例。

**N9 默认关键词表混入占位符「项目名」（2.1.2）**

2.1.2 默认关键词表为「`日报`、`bug`、`上线`、`发布`、项目名」。「项目名」是占位符而非关键词字面量，实现者无法判断是否应把「项目名」三个字当关键词、还是用某个配置值替换。应把真实词与占位符分开：默认表只列真实词，项目名作为必填配置项（如 `project_keywords`）单列。

## 4. 缺失内容（按「能否据此直接实现」的重要性排序，最多 6 条）

1. **接口鉴权与凭据管理**：GitHub REST API 需要 token，但 2.4 只写「GitHub REST API」未提凭据；飞书 app_id/secret、SMTP 账号密码的存放与注入方式（环境变量/密钥文件）均未定义，「SMTP 与飞书凭据引用」的「引用」无 schema。无此无法接通任何数据源。
2. **失败告警出口**：2.1.5 只写「退出码非 0，便于 cron 侧告警」，但 cron 本身不告警，谁监控退出码、通过什么通道通知运维未定义；推送失败最终可能无人知晓。
3. **数据脱敏**：2.1.2 要求输出「原文片段」，原文可能含手机号、密码、token 等敏感信息；无脱敏规则，也无「只采集哪些群」的边界，存在泄露风险。
4. **时区**：00:00、18:00、72 小时均未声明时区；文中提到中国调休，应明确所有时间以 Asia/Shanghai 计，否则跨时区部署或夏令时场景下窗口与触发时间错位。
5. **并发与重跑互斥**：2.1.6 支持重跑，但无锁/互斥机制；两个实例并发执行会同时写 SQLite、同时推送，且与「更新而非新增」的幂等预期冲突。
6. **日志与可观测性**：无日志级别、日志文件路径、失败原因记录（`run` 表只存「成功与否」不存原因）；2.1.5 提到「保留已生成的日报文件」，但文件路径与命名规范全文未定义。
