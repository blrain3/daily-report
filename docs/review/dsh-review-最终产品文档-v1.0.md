# 评审意见：《最终产品文档 v1.0》智能日报生成器

## 1. 总体结论

文档与 `proposal-v1.5.md` 的核心契约基本一致（`run.status` 四值、`push_log.status` 四值、`seen_item.first_seen_report_date` 定义、15/35/45/60/30 秒层级、推送三档判定顺序均已正确落地），技术内容（DDL、流程、图）总体可用且诚实标注「待实现」；但作为「最终产品文档」仍缺目录、版本历史、错误码/退出码、容量与性能、部署回滚、许可证与依赖清单等交付物必备内容。

**可否提交：补齐下列完整性缺口后可提交；当前不建议直接作为最终交付物提交。**

## 3. 技术正确性问题

1. **DDL 可直接执行（已实测通过）**。§4.3 的建表语句在 SQLite 中可完整执行：`INTEGER PRIMARY KEY AUTOINCREMENT`、各 `CHECK`、`GLOB` 校验、`BEFORE UPDATE ... RAISE(ABORT)` 触发器、`push_log_success` 部分唯一索引语法均合法。主键与唯一约束符合规格语义；`run` 终态 CHECK（行 137–142）与 §2.8「`failed` 无文件、`success`/`partial` 落盘后有文件」一致；`push_log` 三组 CHECK（行 195–197）与 §2.7 P1-1 一致。
2. DDL 两处设计约束需注意：`content_sha256` 的 `CHECK (NOT GLOB '*[^0-9a-f]*')`（行 189）只接受**小写**十六进制，实现须保证摘要小写（Python `hashlib` 默认小写，可满足），建议在文档注明或放宽为 `[0-9a-fA-F]`；`push_log_success` 唯一索引保证同键至多一条 `success`，与不变量一致，但要求应用在「正文变化重推」时生成不同的 `content_sha256`，文档已覆盖。
3. §4.4 三条流程与规格时序一致：4.4.1 与 §2.5–§2.11 对齐（启动写 `running` → 补渲染 → 并发采集 → 同事务插入与推进水位 → 渲染落盘 → 终态）；4.4.2 与 §2.3–§2.7 对齐（`item_key` 三式、人员映射、未归属段、渲染筛选、版面提示）；4.4.3 与 §2.7 对齐（三档判定顺序正确，v1.5-r4 的「无 `success` 且有 `sending`」前提已体现）。
4. 一处「建议」未定案写入核心流程：行 231「入库事务提交后若渲染失败，建议……还原本轮已推进的水位」在规格中**未规定**。规格 §2.8 只保证「插入与推进同事务」，未覆盖「事务已提交、随后渲染失败」场景；若实现按文档建议回滚，可满足 §2.8「`failed` 不推进任何水位」，但该条目前只是建议。应先把此规则写入规格（或明确「待实现阶段确认」），否则实现存在两可。
5. 图与正文对照：
   - `arch.puml` 的「归属与去重层」**没有任何入边**（既无 采集层→归属，也无 运行编排→归属），与正文 §4.1 行 75「归属与去重层依赖采集结果」不符，数据流不闭合。
   - 分层命名与「工作日判定」位置与正文不一致（见一致性表 1、2）。
   - `sequence.puml` 与 §4.4.1 一致；未画出 45 秒降级细节与「仅由 `failed`/`running` 形成的补渲染候选须有该日已入库记录」的条件，属简化，可接受。
   - `push-state.puml` 与 §4.4.3 基本一致；漏「failed 与 superseded 并存」「仅 superseded 记 WARN」两细节（见一致性表 8、9）。另 `Sending→Success` 标注「事务内结清旧行为 superseded」把分支 2（只结清旧 `sending`）与分支 3（结清 `failed`/`sending`/`superseded` 全部残留）合并成一句，建议拆分标注，避免实现误解。

## 4. 完整性缺口（按重要性排序）

1. **目录（TOC）**：全文无目录，509 行、20+ 张表，无导航。
2. **本文档版本历史**：§1 只有「v1.0」单行，无本评审对象自身的修订记录（规格 §6 有版本变更记录，产品文档却缺失）。
3. **运行接口契约（退出码/错误码/告警报文格式）**：退出码仅散见（行 225、229、412），无集中契约表；错误码未定义；「已有实例在运行」「数据获取失败：<原因>」等消息文本未写全。
4. **容量与性能预算**：仅 §6.1 有「5 人、每类各 ≤50 条、<60 秒」一条目标；缺 5–15 人峰值负载、分页规模、SQLite 体积与数据保留、GitHub/飞书 API 配额与限流余量等估算。
5. **部署回滚与备份**：§5.3 有部署方式，无回滚方案，也无数据库、`reports/`、配置文件的备份/恢复说明。
6. **许可证与依赖清单**：无依赖清单（`requirements.txt`、Python-Markdown 版本等）与许可证说明，§5.3 仅提「安装锁定版本的 Python 依赖」。

（次要与已部分覆盖：安全与隐私除凭据注入与脱敏外，无数据保留、审计、日志留存说明；测试数据与 fixture 只引用规格 §3.6 夹具，本仓库未附对应 fixture 文件。）

## 5. 诚实性核查

- 行 13、15–26 明确「产品状态：设计定稿，待实现」「系统尚未编写代码」——与事实一致。
- §6.2 证据表全部标「待补充截图」「待实现」，无虚构截图、测试结果或性能数字。
- 未发现「未实现却写成已实现」；行 207（`render_metadata` 扩展）、行 231（渲染失败回滚）均用「建议」明示未定案内容，诚实。
- 结论：**诚实性通过**。建议把两处「建议」事项改为定案写入规格，或在文档中标注「待实现阶段确认」，避免评审与实现口径不一致。

## 6. 可读性与规范

- 章节编号连续（1–7 + 附录 A/B），图编号 A-1/A-2/A-3 连续且正文有引用，可正常定位。
- 术语总体统一：全文用「报告日」未混用「日报日期」，用「水位」未混用「水位线」，用「未归属段」；「未匹配」仅作修饰语。「首次入库」（行 44、57、240、264）与「首次入报」（行 431）轻微不一致，建议统一为「首次入库」。
- 表格共 20+ 张但均无表号，交叉引用只能写「见规格 §x」，建议给表格编号。
- 15/35/45/60/30 五个数值散落于 §4.4.1、§4.4.3、§6.1，无规格 §2.11 式的「一句话结论 + 小表」总览，层级关系读起来不直观。
- 篇幅 509 行、密度高、空话少，整体可读性良好。
