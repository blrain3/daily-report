# 《智能日报生成器》proposal-v1.2 独立评审

v1.2 补齐了配置结构和多项验收判据，但正常执行仍会漏采，同日重跑可能覆盖完整日报，飞书采集与归属也缺少可验证的接口契约，**暂不可直接进入实现**。

## 闭环核验表

### N1–N9

| 条目 | 判定 | v1.2 原文与核验 |

## 一致性问题

1. **窗口术语统一了，边界和数据源覆盖仍不统一。** §2.5、§3.3 与 §4 都指向上次成功执行时间及 72 小时截断，§2.6 与 §3.4 也统一按窗口判断成员是否有记录。实际按 §2.5 执行，前次 `18:00:00` 启动、`18:00:35` 成功结束，前次只采到 `18:00:00`，本次却从 `18:00:35` 开区间起算，中间 35 秒漏采。§3.3-4 还把 `finished_at` 无条件写成下次起点，§2.5 对超过 72 小时另有截断。§2.3 和 §3.2 对提交、任务明确应用窗口，对群消息只写白名单和关键词，群消息是否按发言时间应用同一开闭边界，文档未定义。§1.2 的「当天的工作数据」若按自然日理解，也与跨日窗口有偏差。
2. **重跑、重生成和补发共用一个说法。** §2.7 和 §3.5 描述按通道跳过成功键及补发失败通道，§2.5 仍为每次启动计算窗口，§2.8 与 §2.10.4 又要求更新当天记录和覆盖当天文件。成功后重跑可能只生成增量甚至空报，再覆盖当天完整日报。单通道失败后重跑时，若正文因上界推进而变化，先前成功通道也会得到新键并再次发送。§2.7、§3.5 的“内容未变不重推”也需要补上“该通道已有同键成功记录”，否则与失败通道补发条款冲突。
3. **GitHub 作者字段一致，飞书身份分支不一致。** GitHub 在 §2.3、§2.4 都使用 `author.login`。飞书在 §2.4 表格及 §3.2 写「仅返回显示名时」才走姓名匹配，§2.4 后续文字却允许「成员未配置 `feishu_open_id`」时回退。返回 ID 和显示名、ID 未命中的样例会有两种结果。两类飞书端点分别返回什么身份字段、消息发送者 ID 的类型、如何取得显示名，文档未定义。§5 所指的 `members.yaml.example` 仍写「该成员只参与代码提交部分」，与 §2.1、§3.1 的姓名回退冲突。§2.1 也未定义重复 `feishu_open_id` 如何处置。
4. **15、20、45、60 秒各有名称，尚未组成同一时序。** §2.11 把 45 秒定为降级阈值，60 秒定为无故障基准的写盘目标。若 15 秒按尝试计，初次加三次重试与 `2/4/8` 秒退避可达 74 秒，45 秒就必须能中止已经在途的调用。若 15 秒是整条数据源的期限，20 秒退避上限和 45 秒降级各管什么仍需定义。§2.11 只说「放弃剩余重试」，未定义是否取消在途调用。§3.7-2 又把 60 秒终点改为进程退出，按主流程会计入写盘后的 SMTP、飞书推送，文档未定义两者的发送超时。
5. **交叉引用的章节目标正确，个别条目编号与落点说明失真。** §2.1→§2.4、§2.2→§2.3、§2.3→§2.4/§2.11、§2.7→§2.9/§2.10.3、§2.10.4→§2.8、§2.11→§3.7 首条、§3.7→§2.11，以及术语表与 §5 的引用均能定位到相关内容。§6 的「3.1-4」若按 v1.2 编号读取，指的是缺 `email`，原“成员文件错误”验收已移到 §3.1 第 6 条。§6 对 N8 的说明「3.3 改为按 2.5 窗口规则推导」也未反映仍保留的周五参照。配套 `holidays.yaml` 的 `year: 2027` 下两个列表均为空，按 §2.9 可用于其他年份的未覆盖回退，但不能直接作为 §3.6 的节假日或调休上班用例。

## 新问题

| 级别 | v1.2 新引入的缺陷 | 实现影响 |
|---|---|---|
| **P0** | **用上次 `finished_at` 作为下界、本次启动时间作为上界。** | 每次成功执行都可能留下永久漏采区间，窗口算法与验收必须一起改。 |
| **P0** | **基于成功记录推进水位，但降级出报的成功条件未定义。** | §2.11 允许缺源出报。若记为 `success`，故障数据源的未采区间可能被跳过。若记为 `failed`，下一次又可能重新纳入已随部分日报发出的记录。全局或逐源水位的选择会改变存储与补采实现。 |
| **P0** | **新增的内容键与同日覆盖机制缺少共同的日报版本。** | 重跑可能覆盖已发出的完整日报，补发通道也可能收到与首发通道不同的正文。需要先定重跑读取哪个窗口、哪个版本，以及何时允许替换当天文件。 |
| **P1** | **`push_log` 缺少外部发送结果不确定时的恢复规则。** | 外部已接收但进程在本地记成功前崩溃，下一次可能重复发送。§2.7 未定义此时如何恢复，也未定义 `member_set` 拼接的分隔和转义，后续修订会影响日志键的兼容性。 |
| **P1** | **新增脱敏规则与 80 字摘录缺少处理顺序。** | 若先截断，跨越第 80 字的手机号或无前缀长密钥可能变成无法识别的片段并出报。处理顺序会影响入库、Markdown 和邮件的共同输出。 |

## 实施阻塞点

配置加载、排他锁和日报模板可以先写。以下问题仍会改变主流程或存储设计，按阻塞程度排序。

1. **确定采集水位与成功条件。** 下一窗口是否接续上一次 `window_end`？降级出报、全源失败、单通道推送失败时分别如何记 `run.status`，各数据源的未采区间如何补回？
2. **确定同日重跑和补发语义。** 默认是重发同一版、重算当天整报，还是生成增量？如何选择待补发正文、保护当天历史产物，并处理发送结果不确定的情况？
3. **确定飞书接口契约。** 用哪些接口或事件来源取得任务创建和历史状态变更、变更时间、负责人及群消息发送者？同一任务多次命中和有 ID 但未匹配时，预期产物分别是什么？
4. **确定执行期限。** 15 秒的计时单位是什么，45 秒是否取消在途调用，两种 60 秒口径分别什么时候适用，推送及告警的超时如何配置？
5. **确定可部署的运行契约。** 告警走哪个独立目标、从哪里读取配置，cron 如何固定 Asia/Shanghai 与工作目录，SQLite 和相对输出路径落在哪里？
