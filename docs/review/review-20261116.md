# 《智能日报生成器》规格评审意见

评审对象：`proposal-v1.0.md`（规范驱动开发 第 4 章练习稿）
评审日期：2026-11-16
结论：**方向可行，但有 4 处必须解决的矛盾/缺口，2 处建议澄清。修订后可进入实现。**

---

## P0 必须解决

### 1. 范围自相矛盾：「不做智能摘要」vs「提取讨论摘要」

- 原文 2.2：不做智能摘要和 AI 总结（本期只做数据整理，不做语义理解）
- 原文 2.1：从飞书群消息中提取与项目相关的讨论摘要

两者不能同时成立。**建议改写为**：

> 从飞书群消息中按关键词表（如 `日报`、项目名、`bug`、`上线`）匹配当天消息，命中后按发送人聚合，输出**原文片段**（保留发言时间、发送人、前 80 字），不做概括、改写或归类。

这样既满足「不含语义理解」，也让验收标准可判定：命中消息数与日报中出现的片段数一致。

### 2. 采集窗口定义冲突

- 验收标准：获取「过去 24 小时内」的 commit
- 术语定义：采集窗口默认「当天 00:00 至执行时刻」

周一执行时，「过去 24 小时」会漏掉周六日；「当天 00:00」则天然覆盖 0 点后的工作。二者必须择一，并补规则：

> **采集窗口 = 上一工作日 00:00 至本次执行时刻**；若上次执行失败，窗口回溯至最后一次成功执行的时刻，最长回溯 72 小时，超出部分在日报中标注「窗口已截断」。

同时删除验收标准里的「过去 24 小时」，改为「采集窗口内的全部 commit」。

### 3. 「成员」缺少配置入口

术语表把成员定义为「配置了 GitHub 与飞书账号映射关系的人」，但 2.1 功能范围里没有任何配置方式。没有它，commit 作者（`zhangsan`）、飞书任务负责人（`张三`）、群消息发送人（`@张三`）无法归属到同一个人，按成员分段的日报就做不出来。

**建议新增功能条目**：

> **成员配置**：以 `members.yaml` 为准，每项包含 `name`（显示名）、`github`（GitHub 用户名）、`feishu_open_id`（飞书 open_id）、`email`（收件地址）。启动时校验：`github` 字段不得重复，缺失 `feishu_open_id` 的成员只参与代码提交部分，并在日报中标注「无飞书绑定」。

对应新增验收标准：配置文件缺字段时，程序启动即报错并指出行号；未绑定飞书的成员不会导致整体生成失败。

### 4. 「非工作日不触发」缺少节假日数据源

crontab 只能表达「周一到周五」，中国调休会把这条验收标准变成假通过（例如调休上班的周六不生成日报）。

**建议明确**：

> 节假日判断以内置 `holidays.yaml`（每年初维护，含法定节假日与调休上班日）为准；cron 每日 18:00 触发，程序读取配置后决定是否执行，周末仅在 `workday: true` 的调休日执行。

对应新增验收标准：给定 2027 年节假日表，调休上班的周六应生成日报，法定节假日应跳过且不发送邮件。

## P1 建议澄清

### 5. SQLite 存了却不用

2.3 要求本地 SQLite 存储日报历史，2.2 又排除「历史日报的搜索和统计分析」。当前形态下数据库只剩「写入」一个用途，属于无效组件。
两个选择，选一个写清：
- **砍掉存储**：日报不落库，只发邮件与飞书消息（最简）
- **保留存储并加一条验收**：`daily_report` 表按 `(date, member)` 唯一，重跑同一天不产生重复记录（为将来补发/查错留余地）

建议选后者，成本低且避免重跑污染。

### 6. 限流重试与 60 秒性能目标可能冲突

验收要求单次生成 < 60 秒，同时又要求 GitHub 限流时最多重试 3 次。指数退避若按 2/4/8 秒，单个数据源就可能吃掉 14 秒；三路并发下仍可能突破 60 秒。

**建议补一句约束**：

> 每个数据源独立超时 15 秒，重试总等待不超过 20 秒；整体超过 45 秒时放弃剩余重试，已获取部分照常出报，未获取部分标注「数据获取失败」。

## 可保留的优点（不用改）

- 三块数据源（代码/任务/沟通）与三段日报一一对应，结构清晰，便于验收。
- 「采集失败标注而非静默跳过」这条边界场景写得具体，很多规格会漏。
- 「不做什么」列了 5 条明确排除项，范围控制得当。
- 技术约束写清了 Python 3.11+、Docker、cron，没有常驻服务，运维成本可控。
