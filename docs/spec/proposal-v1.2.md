# 智能日报生成器

## 1. 背景与目标

### 1.1 背景
团队每天需要花 15-30 分钟手写日报，内容包括当天的代码提交、任务进展和协作沟通。这个过程重复、低效，且经常因为遗忘而不完整。团队 Leader 需要了解每个人的工作进展，但手写日报的信息密度低、格式不统一，阅读体验差。

### 1.2 目标
构建一个自动化工具，从团队现有的协作平台中收集当天的工作数据，自动生成结构化的日报，并推送给相关人员。

### 1.3 目标用户
- **主要用户**：5-15 人的研发团队成员（日报的数据来源）
- **主要读者**：团队 Leader / 项目经理（日报的消费者）

## 2. 功能范围

### 2.1 成员配置

系统以仓库根目录的 `members.yaml` 为成员唯一来源，启动时加载并校验。字段如下：

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 日报中显示的姓名，全局唯一，同时用于飞书显示名回退匹配（见 2.4） |
| `github` | 是 | GitHub 用户名，全局唯一，用于匹配 commit 作者 |
| `feishu_open_id` | 否 | 飞书 open_id，用于匹配任务负责人与群消息发送人；缺失的成员仍参与代码提交与显示名回退匹配 |
| `email` | 否 | 个人收件地址，为后续「按成员推送个人日报」预留，**本期不消费**；若填写则必须是合法邮箱格式 |

校验规则：

- `name` 或 `github` 缺失、重复时，程序启动即失败并打印重复/缺失项所在行号。
- `email` 缺失时正常启动（可选字段）；填写但格式非法时启动失败并打印行号。
- `feishu_open_id` 缺失的成员仍参与代码提交部分，日报中标注「无飞书绑定」；仍可通过显示名参与任务/消息归属（见 2.4）。
- 文件不存在或 YAML 解析失败时启动失败，不进入采集阶段。

### 2.2 应用配置与凭据管理

`config.yaml` 保存非敏感配置；**所有凭据一律通过环境变量注入，`config.yaml` 只保存环境变量名，不保存任何明文凭据**。`config.yaml`、`members.yaml` 示例文件与任何密钥文件均不得包含真实凭据，且不进入版本控制（部署侧通过 `.gitignore` 排除，运维在运行环境中注入环境变量）。

字段表：

| 字段 | 必填 | 说明 |
|---|---|---|
| `project_name` | 是 | 项目名，单列配置项；程序将其自动作为项目专属关键词加入消息匹配（见 2.3），并写入日报标题 |
| `repos` | 是 | 配置仓库列表，字符串列表，格式为 `owner/repo`（如 `acme/daily-report`） |
| `keywords` | 否 | 消息采集关键词表，字符串列表；缺省为 `[日报, bug, 上线, 发布]` |
| `github.token_env` | 是 | GitHub token 所在的环境变量名（如 `DAILY_REPORT_GITHUB_TOKEN`） |
| `feishu.app_id_env` | 是 | 飞书 app_id 所在的环境变量名 |
| `feishu.app_secret_env` | 是 | 飞书 app_secret 所在的环境变量名 |
| `feishu.collect_chat_ids` | 是 | 允许采集的群 chat_id 白名单列表；白名单外群的消息一律不采集（见 2.3） |
| `feishu.notify_chat_id` | 是 | 日报推送目标群 chat_id |
| `smtp.host` | 是 | SMTP 服务器地址 |
| `smtp.port` | 是 | SMTP 端口 |
| `smtp.use_tls` | 是 | 是否使用 TLS（true/false） |
| `smtp.username_env` | 是 | SMTP 用户名所在的环境变量名 |
| `smtp.password_env` | 是 | SMTP 密码/授权码所在的环境变量名 |
| `smtp.from` | 是 | 发件人地址 |
| `smtp.leader_to` | 是 | Leader 汇总邮件收件地址，独立配置，不占用成员 `email` |
| `report_dir` | 否 | 日报文件输出目录，默认 `./reports` |
| `log.level` | 否 | 日志级别（DEBUG/INFO/WARNING/ERROR），默认 `INFO` |
| `log.dir` | 否 | 日志目录，默认 `./logs` |
| `lock_file` | 否 | 单实例锁文件路径，默认 `/tmp/daily-report.lock` |

示例：

```yaml
project_name: 智能日报
repos:
  - acme/daily-report
  - acme/backend
keywords:
  - 日报
  - bug
  - 上线
  - 发布
github:
  token_env: DAILY_REPORT_GITHUB_TOKEN
feishu:
  app_id_env: DAILY_REPORT_FEISHU_APP_ID
  app_secret_env: DAILY_REPORT_FEISHU_APP_SECRET
  collect_chat_ids:
    - oc_xxxxxxxxxxxxxxxx
  notify_chat_id: oc_yyyyyyyyyyyyyyyy
smtp:
  host: smtp.example.com
  port: 465
  use_tls: true
  username_env: DAILY_REPORT_SMTP_USER
  password_env: DAILY_REPORT_SMTP_PASSWORD
  from: daily-report@example.com
  leader_to: leader@example.com
report_dir: ./reports
log:
  level: INFO
  dir: ./logs
lock_file: /tmp/daily-report.lock
```

启动时校验 `config.yaml` 必填项；缺失时启动失败并指出缺失项。引用的环境变量不存在或为空时，启动失败并在日志说明缺少哪个变量。

### 2.3 数据采集

- **代码提交**：通过 GitHub REST API，按 `members.yaml` 中每个 `github` 用户过滤，查询其在 `config.yaml` 配置仓库列表内、采集窗口内的提交。字段为 `sha`、`message` 首行、`author.login`、`committed_at`、`additions`/`deletions`。**仅采集作者（`author.login`）在 `members.yaml` 中登记的提交**；作者不在成员表中的提交不采集。GitHub 字段名以 GitHub 官方 API 文档为准，实现时核对实际返回字段。
- **任务进展**：通过飞书开放平台任务接口，获取采集窗口内发生以下任一事件的任务：**创建、状态进入「进行中」、状态进入「已完成」**，字段为任务标题、负责人、变更前后状态、变更时间。负责人按 2.4 映射到成员。
- **协作沟通**：从 `feishu.collect_chat_ids` 白名单群的消息中，按**关键词表**（`keywords` + `project_name` 自动加入）匹配，命中后按发送人聚合，输出**原文片段**——保留发言时间、发送人、正文前 80 字。发送人按 2.4 映射到成员。
- **飞书 token 刷新**：飞书 API 调用统一经过 token 管理。当接口返回表明 token 失效的响应（如 401 或文档定义的失效错误码，以飞书开放平台文档为准）时，自动刷新一次 token 并重试该请求；刷新失败按该数据源失败处理。刷新与重试的耗时计入该数据源 15 秒超时与重试预算（见 2.11）。

**采集范围边界与脱敏**：

- 群消息只采集 `feishu.collect_chat_ids` 白名单内的群；白名单外群的消息不采集、不入库、不出报。GitHub 只采集 `repos` 列表内的仓库。
- 所有进入 SQLite 与日报的原文，在写入前统一应用脱敏规则：
  - 手机号：匹配 11 位大陆手机号形态，中间四位替换为 `****`（如 `138****1234`）。
  - token/密钥形态：`ghp_`、`sk-`、`Bearer ` 等已知前缀后的值，以及长度 ≥ 20 的连续字母数字/`_-` 串，替换为 `<REDACTED>`。
  - 密码形态：`password`、`passwd`、`pwd`、`token`、`secret` 后跟 `=` 或 `:` 的值，替换为 `<REDACTED>`。

### 2.4 成员归属映射

日报按「每位成员一段」组织，数据必须先映射到 `members.yaml` 成员。映射关系如下：

| 数据源 | 接口返回字段 | 匹配到 `members.yaml` 字段 | 匹配规则 |
|---|---|---|---|
| GitHub commit 作者 | `author.login`（GitHub API 返回的提交作者登录名；以 GitHub 官方文档为准，实现时核对） | `github` | 精确匹配；`author.login` 为空或不在成员表中的提交不采集 |
| 飞书任务负责人 | 负责人的 open_id 或显示名（字段名以飞书开放平台文档为准，实现时以实际返回字段核对） | 优先 `feishu_open_id`，回退 `name` | 接口返回 open_id 时与 `feishu_open_id` 精确匹配；仅返回显示名时与 `name` 精确匹配 |
| 飞书群消息发送人 | 发送人的 open_id 或显示名（同上，以实际返回字段核对） | 优先 `feishu_open_id`，回退 `name` | 同任务负责人规则 |

回退匹配策略：优先使用 open_id 匹配 `feishu_open_id`；当接口不返回 open_id 或成员未配置 `feishu_open_id` 时，使用显示名与 `name` 精确匹配。由于 `name` 全局唯一，显示名匹配不存在同名歧义。

**未匹配去向**：任务与群消息经上述规则均无法匹配到任何成员时，**进入日报对应部分的「未归属」段**（任务进展与协作沟通两部分末尾各一个「未归属」小节），不丢弃、不做计数后丢弃；原文片段同样经过 2.3 的脱敏规则。

### 2.5 采集窗口

**定义：采集窗口 = (上次成功执行时刻, 本次执行时刻]，即不含上次成功执行时刻、含本次执行时刻，避免边界记录重复计入相邻两天。**

- 「上次成功执行时刻」取 `run` 表中最近一条 `status = success` 记录的 `finished_at`。
- 「本次执行时刻」取程序启动时读取的当前时间（Asia/Shanghai），全程使用同一值。
- 每次执行成功后写入一条 `run` 记录（含 `finished_at`），作为下次窗口起点；执行失败不写成功记录、不推进窗口起点。

起点判定分三种情形：

1. **存在上次成功记录且距今 ≤ 72 小时**：窗口起点 = 上次成功执行时刻。周一执行时窗口起点即上一工作日的成功执行时刻，自然覆盖周末，且不与上一工作日日报重叠。
2. **首次运行或 `run` 表无任何成功记录**：窗口起点 = 上一工作日 00:00（Asia/Shanghai）；若该起点早于「本次执行时刻 − 72 小时」，则起点改为「本次执行时刻 − 72 小时」，并在日报对应段落标注「窗口已截断，更早记录未包含」。
3. **上次成功记录距今 > 72 小时**：窗口起点 = 本次执行时刻 − 72 小时，并在日报对应段落标注「窗口已截断，更早记录未包含」。

窗口按上述规则推导，跨越周末或节假日时自然覆盖整个间隔，不做额外按天截断。

### 2.6 日报生成

- 将采集到的数据按「代码提交 → 任务进展 → 协作沟通」三部分组织，每位成员一段。
- 成员在**采集窗口内**无任何记录时，该段输出「今日无记录」，不省略该成员。
- 任务进展与协作沟通部分末尾，若存在 2.4 所述的未匹配记录，则各追加一个「未归属」小节。
- 输出格式为 Markdown，同时渲染为 HTML 邮件正文；入报原文均为脱敏后文本。

### 2.7 推送与幂等

- 每个**工作日** 18:00（Asia/Shanghai）触发，是否真正执行由程序按 2.9 判定。
- 通过 SMTP 向 Leader 发送 HTML 格式日报；Leader 收件地址来自 `smtp.leader_to`，不占用成员 `email`。
- 通过飞书机器人把 Markdown 日报发到 `feishu.notify_chat_id` 指定群。

**推送幂等机制**：新增 `push_log` 表，以推送键判断是否需要重推。推送键 = `(report_date, member_set, content_sha256)`：

- `report_date`：日报对应日期（Asia/Shanghai）。
- `member_set`：参与日报的成员集合的规范化串（成员 `name` 排序后拼接）。
- `content_sha256`：该通道待推送正文（HTML 或 Markdown）的 SHA-256 摘要。

重跑同一天时的行为：

- 对每个通道（SMTP、飞书）分别计算推送键。若 `push_log` 中已存在**同键且状态为 `success`** 的记录，则该通道跳过，**不重推**。
- 若内容未变则不重推；若成员集合或内容变化（推送键变化）则**重推**，并在 `push_log` 追加一条记录（含推送键、通道、状态、失败原因、时间）。
- 历史推送失败的通道（无 `success` 记录）在重跑时重推，成功后补记 `success`。
- 推送失败时保留已生成的日报文件，进程退出码非 0，由 2.10.3 的包装脚本告警。

### 2.8 运行记录与日报存储

本地 SQLite 保存三张表：

| 表 | 用途与关键字段 |
|---|---|
| `run` | 每次执行记录：`id`、`started_at`、`finished_at`、`window_start`、`window_end`、`status`（success/failed）、`report_file`、`failure_reason`（失败原因汇总）、各数据源状态与错误原因（`github_status/github_error`、`feishu_task_status/feishu_task_error`、`feishu_message_status/feishu_message_error`、`smtp_status/smtp_error`、`feishu_push_status/feishu_push_error`） |
| `daily_report` | 日报内容，按 `(date, member)` 唯一；重跑同一天时更新既有记录而非新增 |
| `push_log` | 推送幂等与审计：`id`、`report_date`、`channel`、`member_set`、`content_sha256`、`status`、`error`、`pushed_at` |

### 2.9 节假日与触发规则

cron 每日 18:00（Asia/Shanghai）触发一次，**是否真正执行由程序读取 `holidays.yaml` 判定**，不依赖 crontab 的星期字段（否则调休场景下「非工作日不触发」会被绕过）。

`holidays.yaml` 每年初维护，结构：

```yaml
year: 2027
holidays:            # 法定节假日，不生成日报
  - date: 2027-01-01
    name: 元旦
workdays:            # 调休上班日，即使是周末也生成日报
  - date: 2027-02-06
    name: 春节调休
```

节假日日期以国务院办公厅当年通知为准，由维护者手工填写。**文件缺失或未覆盖当年时**，程序按周一至周五工作日执行，并在日报页脚标注「节假日表未覆盖，已按默认工作日判断」。

### 2.10 运行保障

#### 2.10.1 时区
所有时间均以 **Asia/Shanghai（UTC+8）** 计：采集窗口边界、18:00 触发时刻、72 小时阈值、日志时间戳、日报日期。程序显式设置时区，不依赖服务器本地时区。

#### 2.10.2 并发与重跑互斥
同一时间只允许一个实例运行。程序启动时以排他方式获取锁文件（`lock_file`，建议 `flock`）；获取失败立即退出（退出码非 0，日志 ERROR 记录「已有实例在运行」），不采集、不写库、不推送。锁在进程结束时自动释放，崩溃时由操作系统释放文件锁。

#### 2.10.3 失败告警出口
程序本身以退出码 0/非 0 表示成功/失败。部署随附包装脚本 `bin/run_daily.sh`：执行程序，捕获退出码；**退出码非 0 时**通过飞书机器人告警群（或 SMTP）向运维发送告警，内容含退出码、日报日期、失败摘要与日志路径。cron 指向包装脚本而非直接指向 Python：

```
0 18 * * * /opt/daily-report/bin/run_daily.sh >> /opt/daily-report/logs/cron.log 2>&1
```

#### 2.10.4 日志与可观测性
- 日志级别：`log.level`（DEBUG/INFO/WARNING/ERROR），默认 INFO。
- 日志路径：`log.dir`，默认 `./logs`；日志文件按天命名 `logs/daily-report-YYYYMMDD.log`。
- 日报文件：`report_dir`，默认 `./reports`；命名 `reports/daily-report-YYYYMMDD.md`，同一天重跑覆盖同一天文件。
- `run` 表记录各数据源成功与否与失败原因（`failure_reason` 及各 `*_error` 字段，见 2.8）；推送失败原因记入 `push_log.error`。

### 2.11 超时与重试预算

- 每个数据源（GitHub / 飞书任务 / 飞书消息）独立超时 15 秒，三路并发执行。
- 单个数据源重试最多 3 次，重试总等待不超过 20 秒（指数退避 2/4/8 秒但受总预算封顶）。
- 整体耗时超过 45 秒时放弃剩余重试，用已获取部分出报；未获取的数据源在该段标注「数据获取失败：<原因>」，不静默跳过。
- 飞书 token 刷新与刷新后的重试计入该数据源 15 秒超时与重试预算。
- 45 秒是降级阈值；60 秒是基准负载下「从进程启动到日报文件写盘（不含 SMTP 与飞书推送）」的耗时上限（见 3.7-1）。

### 2.12 不做什么（本期明确排除）

- **不做**智能摘要和 AI 总结（只做关键词匹配与原文摘录，不做语义理解、不调用大模型）
- **不做**移动端 App
- **不做**历史日报的搜索、统计与可视化（存储仅用于去重、补发与审计，不提供查询界面）
- **不做**个人日报的编辑和补充功能
- **不做**多团队 / 多租户支持

### 2.13 技术约束

- 后端语言：Python 3.11+
- 部署环境：公司内网服务器（Docker 容器）
- 外部依赖：GitHub REST API、飞书开放平台 API、SMTP
- 运行方式：cron 每日触发一次（经 `bin/run_daily.sh` 包装脚本），无常驻服务
- 数据存储：本地 SQLite（`run`、`daily_report`、`push_log` 三张表）
- 配置：`members.yaml`、`holidays.yaml`、`config.yaml`；凭据经环境变量注入，不落盘、不入库

## 3. 验收标准

### 3.1 成员配置

- [ ] `members.yaml` 缺 `name` 或 `github` 时，程序启动失败并指出行号
- [ ] 两个成员 `github` 重复时，启动失败并指出重复项
- [ ] 两个成员 `name` 重复时，启动失败并指出重复项
- [ ] 成员缺 `email`（可选字段）时正常启动、正常出报
- [ ] 成员 `email` 填写但格式非法时，启动失败并指出行号
- [ ] `members.yaml` 不存在或 YAML 解析失败时，程序退出码非 0，且不生成日报文件、不写入 SQLite、不发送邮件与飞书消息
- [ ] 成员缺 `feishu_open_id` 时正常出报，该成员段落标注「无飞书绑定」，且仍可通过显示名参与任务/消息归属

### 3.2 数据采集与归属映射

- [ ] 对每个成员的 `github` 用户，获取其在配置仓库、采集窗口内的全部 commit；且不采集作者不在 `members.yaml` 中的提交
- [ ] 获取采集窗口内满足以下任一事件的任务：创建、状态进入「进行中」、状态进入「已完成」，并返回任务标题、负责人、变更前后状态、变更时间
- [ ] 从白名单群按关键词表匹配消息，输出原文片段；命中消息数与日报中出现的片段数一致（含「未归属」段）
- [ ] 任一数据源超时或报错时，其余数据源照常入报，失败段标注「数据获取失败：<原因>」
- [ ] 飞书任务返回 open_id 时按 `feishu_open_id` 匹配；仅返回显示名时按 `name` 精确匹配
- [ ] 任务负责人或群消息发送人无法匹配到任何成员时，进入对应部分的「未归属」段，不丢弃

### 3.3 采集窗口

- [ ] 存在上次成功记录且距今 ≤ 72 小时时，窗口起点 = 上次成功执行时刻；周一执行时窗口覆盖周末且不与周五日报重叠
- [ ] 首次运行或 `run` 表无成功记录时，窗口起点 = 上一工作日 00:00；若超过 72 小时则截断为最近 72 小时并标注
- [ ] 上次成功记录距今 > 72 小时时，窗口截断为最近 72 小时，日报标注「窗口已截断，更早记录未包含」
- [ ] 每次执行成功后 `run` 表写入 `finished_at`，作为下次窗口起点；失败执行不推进窗口起点

### 3.4 日报与推送

- [ ] 生成的日报包含三个部分：代码提交、任务进展、协作沟通
- [ ] 采集窗口内无任何记录的成员显示「今日无记录」，不被省略
- [ ] 用指定的 Markdown→HTML 渲染器渲染无错误；日报中无未闭合代码块、无表格错位；HTML 在目标邮件客户端可正常展示
- [ ] Leader 收到 HTML 格式日报邮件
- [ ] 飞书机器人成功将日报发送到指定群
- [ ] SMTP 与飞书任一通道失败即视为推送失败，进程退出码非 0；已生成的日报文件保留在配置的 `report_dir`

### 3.5 存储与推送幂等

- [ ] 同一 `(date, member)` 重跑两次，`daily_report` 中只有一条记录
- [ ] `run` 表可查到每次执行的时间、窗口起止、各数据源状态与失败原因
- [ ] 重跑同一天且内容未变时，SMTP 与飞书通道均不重推，`push_log` 不新增 `success` 记录
- [ ] 重跑同一天且内容变化（成员集合或任一成员段落变化）时，对应通道重推，`push_log` 追加记录
- [ ] 历史推送失败的通道在重跑时重推，成功后 `push_log` 补记 `success`

### 3.6 节假日

- [ ] 给定节假日表，法定节假日不生成、不推送日报
- [ ] 调休上班的周六正常生成并推送
- [ ] 未配置当年节假日表时，按周一至周五执行并在页脚标注
- [ ] `holidays.yaml` 文件缺失时，按周一至周五执行并在页脚标注

### 3.7 性能与稳定性

- [ ] 在无故障、每个成员 ≤ 50 条 commit/任务/消息的基准负载下，从进程启动到日报文件写盘（不含 SMTP 与飞书推送）耗时 < 60 秒；45 秒后按 2.11 触发降级
- [ ] 注入 GitHub 限流（429）后，该数据源重试 ≤ 3 次且重试等待 ≤ 20 秒；进程在 60 秒内结束，日报含「数据获取失败：<原因>」，其余数据源内容不受影响
- [ ] 飞书 token 过期时自动刷新一次并重试；刷新失败按数据源失败处理；刷新与重试耗时计入该数据源 15 秒/重试预算

### 3.8 配置、凭据与运行保障

- [ ] `config.yaml` 必填项（`project_name`、`repos`、凭据环境变量名等）缺失时，启动失败并指出缺失项
- [ ] 程序仅从环境变量读取凭据；`config.yaml` 与仓库内不出现明文 token/密码
- [ ] 引用的凭据环境变量不存在或为空时，启动失败并在日志说明缺少哪个变量
- [ ] `bin/run_daily.sh` 在程序退出码非 0 时向告警通道发送告警（含退出码、日报日期、失败摘要与日志路径）
- [ ] 原文片段按 2.3 规则脱敏：手机号中间四位为 `****`，token/密码形态字符串替换为 `<REDACTED>`；白名单外群消息不采集
- [ ] 所有时间戳（日志、日报日期、窗口边界）均以 Asia/Shanghai 输出
- [ ] 同时启动两个实例时，第二个实例退出码非 0、日志含「已有实例在运行」，不写库、不推送
- [ ] 日志写入 `logs/daily-report-YYYYMMDD.log`，级别可配；日报写入 `reports/daily-report-YYYYMMDD.md`；`run` 表含 `failure_reason` 及各数据源错误原因字段

## 4. 术语定义

| 术语 | 定义 |
|------|------|
| 日报 | 系统自动生成的每日工作总结，包含代码、任务、沟通三部分 |
| 成员 | 在 `members.yaml` 中登记、具备 GitHub 用户名的工作者 |
| 数据源 | 提供工作数据的外部平台（GitHub、飞书任务、飞书消息） |
| 采集窗口 | (上次成功执行时刻, 本次执行时刻]；首次运行、记录缺失或超 72 小时时按 2.5 回溯/截断 |
| 原文片段 | 见 2.3 |
| 工作日 | `holidays.yaml` 判定为工作的日期；未覆盖当年或文件缺失时退化为周一至周五 |
| 未归属段 | 无法匹配到成员的消息/任务在日报中的统一落段，见 2.4、2.6 |
| 推送键 | `(report_date, member_set, content_sha256)`，用于推送幂等判定，见 2.7 |
| 时区 | 全系统时间以 Asia/Shanghai（UTC+8）计，见 2.10.1 |
